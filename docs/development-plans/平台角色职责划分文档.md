# LabelHub 平台角色职责划分文档

> 本文档定义 LabelHub 数据标注平台中所有用户角色的职责边界、权限范围、注册方式和交互关系。作为前后端开发、权限设计和 UI 路由的唯一参考。

## 一、角色总览

| 角色 | 代码标识 | 定位 | 获取方式 |
|------|----------|------|----------|
| 系统管理员 | `ADMIN` | 平台运维与人员管理 | 系统预置，不开放注册 |
| 任务负责人 | `OWNER` | 业务侧全流程管理者 | 注册时自选，注册后固定 |
| 标注员 | `LABELER` | 数据生产者 | 注册时自选，注册后固定 |
| 人工审核员 | `REVIEWER` | 质量把关者 | 由 ADMIN 帮忙注册，不开放自助注册 |
| AI 审核代理 | `SYSTEM_AGENT` | 系统内置 AI 主体 | 系统启动时自动创建，不可登录 |

## 二、注册与账号规则

### 2.1 注册入口

```
开放注册（二选一，注册后角色固定不可变更）
  ├── OWNER（任务发布端）
  └── LABELER（标注作答端）
```

- 注册页面提供身份选择：「我是任务发布者」/「我是标注员」。
- 选择后角色绑定，不可通过任何途径自行变更。
- ADMIN 也不能将 OWNER 改为 LABELER 或反向操作。

### 2.2 内部账号

| 账号类型 | 创建方式 | 说明 |
|----------|----------|------|
| ADMIN | 系统初始化时 seed | 至少保留一个，不可全部删除 |
| REVIEWER | ADMIN 通过后台「创建审核员」功能注册 | 不走公开注册流程 |
| SYSTEM_AGENT | 应用启动时自动初始化 `system_ai_agent` | `loginEnabled=false`，不可登录 |

### 2.3 多账号切换

- 同一设备（浏览器）支持保存多个已登录账号。
- 提供快捷切换账号功能（非多角色兼任，是独立账号间切换）。
- 切换时清除当前会话状态，加载目标账号的工作台。
- 典型场景：演示时在同一浏览器切换 OWNER 和 LABELER 账号。

## 三、各角色详细职责

### 3.1 ADMIN — 系统管理员

**定位**：平台最高权限管理员，负责平台运维、人员管理和跨角色业务兜底处理。

**核心页面**：Admin 管理后台

#### 功能清单

| 功能域 | 功能项 | 说明 |
|--------|--------|------|
| 用户管理 | 查看用户列表 | 展示所有 OWNER、LABELER、REVIEWER 用户，过滤 SYSTEM_AGENT |
| | 搜索用户 | 按 username / email 搜索 |
| | 启用用户 | 恢复被禁用的用户登录能力 |
| | 禁用用户 | 禁止用户登录，已登录 token 失效 |
| 审核员管理 | 创建审核员账号 | 为 REVIEWER 注册账号（设置用户名、密码、邮箱） |
| 安全约束 | 最后一个 ADMIN 保护 | 禁止移除或禁用最后一个 ADMIN |

#### 权限边界

- ADMIN 继承 OWNER、LABELER、REVIEWER 的业务访问权限，是后端最高权限角色。
- ADMIN 可跨用户访问和处理任务、模板、数据集、提交、审核、导出、奖励等业务资源。
- ADMIN 执行业务操作时仍必须遵守原业务状态机和参数校验，例如非 DRAFT 任务不可按草稿编辑、非 PENDING_FINAL 提交不可审核。
- ADMIN 操作写入审计日志时使用 ADMIN 自己的 userId 作为 actor，不伪装成资源原所有者。
- 不能将 OWNER 改为 LABELER 或反向操作（注册后角色固定）。

---

### 3.2 OWNER — 任务负责人

**定位**：业务侧全流程管理者，负责从任务创建到数据导出的完整链路。

**核心页面**：任务管理 / 模板搭建 / AI 配置 / 数据看板 / 导出

#### 功能清单

| 功能域 | 功能项 | 说明 |
|--------|--------|------|
| 任务管理 | 创建任务 | 标题、描述、富文本说明、标签、配额、截止时间、overlapCount |
| | 编辑任务 | 仅 DRAFT 状态可编辑核心字段 |
| | 发布任务 | 校验数据集、模板、AI 配置、奖励规则均已就绪 |
| | 暂停/恢复/结束 | 按状态机合法路径迁移 |
| 数据集管理 | 导入数据 | 支持 JSON / JSONL / Excel |
| | 预览数据 | 查看 externalId、itemJson 摘要 |
| | 批量编辑 | DRAFT 可编辑/删除/覆盖；PUBLISHED 可追加/修正未领取题 |
| | 错误报告 | 导入失败行记录，可下载错误报告 |
| 模板搭建 | Designer 搭建 | 拖拽物料到画布，配置属性面板 |
| | 保存/fork 版本 | 已发布版本不可修改，需 fork 新版本 |
| | 预览 | 同一份 schema 可在 Designer 中预览渲染效果 |
| | LlmTrigger 测试 | Designer 中可测试字段级 LLM 输出 |
| AI 审核配置 | 选择 Provider/模型 | 从自己管理的 Provider 中选择 |
| | Prompt 模板 | 编写审核 Prompt，支持变量插值 |
| | 评分维度 | 配置评分维度（相关性/准确性/格式合规/安全性等） |
| | 阈值策略 | 通过阈值、人工复核阈值 |
| | Prompt 测试 | 用样本数据测试 Prompt 效果 |
| LLM Provider 管理 | 新增 Provider | 配置 baseUrl、apiKey、modelName、自定义 headers |
| | 编辑 Provider | 修改已有 Provider 配置 |
| | 启用/停用 Provider | 停用后该 Provider 不可用于 AI 审核配置 |
| | 连通性测试 | 验证 Provider 是否可正常调用 |
| | API Key 管理 | 加密存储，不明文返回前端，不写入日志 |
| 奖励规则 | 配置奖励 | 单条通过奖励、虚拟币种名、是否对 Labeler 展示 |
| | 规则冻结 | 任务发布后规则以快照形式保存，不影响历史流水 |
| 数据看板 | 进度统计 | 总题数/已领取/已提交/待审核/通过/打回/AI失败 |
| 数据导出 | 创建导出任务 | 选择格式（JSON/JSONL/CSV/Excel）、字段映射、是否含 AI 审核 |
| | 导出历史 | 查看状态、创建时间、下载链接 |

#### 权限边界

- 只能管理自己创建的任务。
- 不能标注作答（OWNER 和 LABELER 是独立身份）。
- 不能执行审核操作。
- 不能管理用户、不能创建审核员账号。

---

### 3.3 LABELER — 标注员

**定位**：数据生产者，面向标注员和行业专家。

**核心页面**：任务广场 / 标注工作台 / 我的贡献

#### 功能清单

| 功能域 | 功能项 | 说明 |
|--------|--------|------|
| 任务广场 | 搜索任务 | 按关键词、标签筛选 |
| | 任务卡片 | 展示奖励、截止时间、可领取数量 |
| | 领取任务 | 并发安全，不超发，同一用户不重复领取同一 item |
| 标注工作台 | 表单渲染 | 基于模板 schema 的 Renderer 渲染标注页面 |
| | 题目导航 | 上一题/下一题/跳题，导航标识状态 |
| | 草稿保存 | 自动保存（Redis 热缓存 + MySQL 持久化），断网不丢失 |
| | 本地离线草稿 | 浏览器本地存储兜底 |
| | 提交答案 | schema 校验通过后提交，每次形成独立版本 |
| | 提交校验 | 必填/枚举/正则/自定义规则校验，错误提示到字段 |
| LLM 辅助 | 字段级 LlmTrigger | 点击触发模型辅助，结果作为参考展示 |
| | 确认预填 | 用户确认后才可预填到目标字段，不自动提交 |
| 打回修改 | 查看打回理由 | 展示审核员的打回原因 |
| | 重新提交 | 修改后重新提交，版本号递增，旧版本标记 SUPERSEDED |
| 我的贡献 | 概览卡片 | 已领取/已提交/待审核/通过/打回/通过率/累计奖励 |
| | 今日提交 | 当日提交数量 |
| | 近 7 日趋势 | 折线图，无数据日期补零 |
| | 各任务明细 | 按任务维度查看贡献 |
| | 奖励流水 | 正向奖励和冲正记录 |
| | 我的数据列表 | 按状态筛选（已提交/待审核/通过/打回/待修改） |

#### 权限边界

- 只能操作自己领取的 assignment。
- 不能创建任务、搭建模板。
- 不能审核他人提交。
- 不能管理用户。
- 不能查看其他标注员的数据。

---

### 3.4 REVIEWER — 人工审核员

**定位**：质量把关者，由 ADMIN 帮忙注册，全局可审核所有任务。

**核心页面**：审核工作台 / 审核结果列表 / 冲突仲裁

#### 功能清单

| 功能域 | 功能项 | 说明 |
|--------|--------|------|
| 待审列表 | 状态筛选 | 按 PENDING_FINAL / APPROVED / REJECTED 筛选 |
| | 任务筛选 | 按任务维度过滤 |
| | AI 结论筛选 | 按 AI 建议（PASS/FAIL/MANUAL_REQUIRED）筛选 |
| | 冲突筛选 | 筛选存在冲突的样本 |
| 审核详情 | 题目原始数据 | 查看 item 原始内容 |
| | 标注答案 | 查看 Labeler 提交的 answerJson |
| | AI 评分 | 查看 AI 各维度评分和总分 |
| | AI Prompt/响应 | 查看 AI 审核使用的 Prompt 和原始响应 |
| | 历史版本 | 查看提交的所有版本，支持 diff 对比 |
| | 审计时间线 | 查看该提交的完整操作历史 |
| 终审操作 | 通过 | submission → APPROVED，触发 SubmissionApproved 事件 |
| | 打回 | submission → REJECTED，必须附理由，Labeler 可见 |
| 多级审核 | 审核级别流转 | 支持多级审核（初审/复审/终审），由配置 `labelhub.review.default-max-level` 控制级数 |
| | 级别升级 | 当前级别通过后自动升级到下一级，分配新的 Reviewer |
| | 终审通过 | 最高级别通过后 submission → APPROVED |
| 批量审核 | 批量通过 | 逐条处理，部分成功返回 |
| | 批量打回 | 必须有统一理由 |
| | 批量标记人工复核 | 标记需要进一步人工审查的样本 |
| | 批量分配 Reviewer | 将样本分配给指定审核员 |
| | 冲突组限制 | 冲突组不能批量通过，必须单独仲裁 |
| 冲突仲裁 | 冲突组列表 | 查看多人标注不一致的样本组 |
| | 横向对比 | 多版本并排展示 |
| | consensusScore | 展示一致性评分 |
| | 选择金标 | 从多个提交中选择最优作为金标 |
| | 仲裁理由 | 填写选择金标的理由 |

#### 权限边界

- 全局审核权限，可审核所有任务的 PENDING_FINAL 提交。
- AI 结果仅为建议参考，最终决定权在 REVIEWER。
- 不能创建任务、搭建模板、配置 AI 审核。
- 不能标注作答。
- 不能管理用户。

---

### 3.5 SYSTEM_AGENT — AI 审核代理

**定位**：系统内置 AI 主体，不可登录，后台异步执行 AI 预审。

**运行方式**：后台异步流水线，无 UI 页面

#### 功能清单

| 功能域 | 功能项 | 说明 |
|--------|--------|------|
| AI 预审 | 审核任务入队 | Labeler 提交后自动创建 AI 审核任务 |
| | Prompt 构造 | 基于 OWNER 配置的模板和评分维度组装 Prompt |
| | LLM 调用 | 通过 LlmGateway 调用配置的 Provider |
| | 结构化输出 | 使用 Function Calling 输出评分结果 |
| | 结果写入 | AI 评分、各维度得分、结论写入 aiReviewResult |
| 状态推进 | 推进 submission | AI 完成后将 submission 推进到 PENDING_FINAL |
| | AI 结论 | PASS（建议通过）/ FAIL（建议打回）/ MANUAL_REQUIRED |
| 失败兜底 | 指数退避重试 | 超时/限流/失败时自动重试 |
| | 最大重试次数 | 超过上限后标记 MANUAL_REQUIRED |
| | 不阻断人工 | AI 失败不影响 Reviewer 终审 |
| 可追溯性 | AgentRun 记录 | 每次运行产生独立实例，记录输入/输出/状态/耗时 |
| | 审计日志 | 通过 AuditAppender 写审计，带 agentRunId |
| | actorType | 审计中标识为 SYSTEM_AGENT |

#### 约束规则

- 默认策略下 AI 结果只是建议；Owner 可通过 `allowAiDirectApprove`/`allowAiDirectReject` 配置允许 AI 在高置信度时直接通过或打回（由 `aiFlowPolicy` 和 `confidenceThreshold` 共同控制）。
- Prompt 和 rawResponse 必须保存，确保可追溯。
- 失败不能阻断人工审核链路。
- 使用 BE-B 提供的 RateLimitService 控制调用频率。
- 每次重试产生新的 AgentRun 记录。

## 四、LLM 使用场景与角色分工

### 4.1 LLM 使用场景总览

平台中有三个 LLM 使用场景，均依赖 OWNER 管理的 LLM Provider：

| # | 场景 | 课题对应 | 触发者 | 粒度 | 说明 |
|---|------|----------|--------|------|------|
| 1 | AI 自动预审 | 4.4 核心难点 | 系统自动（Labeler 提交后） | 题目级 | 按维度打分，输出通过/打回/人工复核 |
| 2 | LLM 交互组件（LlmTrigger） | 4.2 物料之一 | Labeler 手动 / Owner 预览 | 字段级 | 模板中嵌入的 LLM 组件，输出作为标注参考或预填 |
| 3 | Pre-Annotation（预标注） | 额外加分项 | Labeler 手动 | 题目级 | 一次生成整题建议答案，复用 AI 审核配置 |

### 4.2 各场景详细说明

#### 场景 1：AI 自动预审（课题核心）

```
LABELER 提交答案
  → 系统自动入队
  → SYSTEM_AGENT 读取 OWNER 配置的 AI 审核规则（Provider + Prompt + 维度 + 阈值）
  → 调用 LlmGateway（Function Calling / 结构化输出）
  → 写入 AI 评分结果
  → 推进 submission 到 PENDING_FINAL
  → REVIEWER 可见 AI 评语
```

| 角色 | 职责 |
|------|------|
| OWNER | 配置 AI 审核规则：选择 Provider/模型、编写 Prompt 模板、设置评分维度和阈值 |
| LABELER | 提交答案后自动触发，无需手动操作 |
| SYSTEM_AGENT | 执行 AI 预审，写入结果，推进状态 |
| REVIEWER | 查看 AI 评分和建议，作为终审参考 |

#### 场景 2：LLM 交互组件 / LlmTrigger（课题要求的物料）

```
OWNER 在 Designer 中拖入 LlmTrigger 组件
  → 配置组件属性：Provider、模型、Prompt 模板、目标字段
  → 保存到模板 schema

LABELER 在标注工作台点击 LlmTrigger 按钮
  → 系统读取组件配置中的 Provider 和 Prompt
  → 调用 LlmGateway
  → 返回结构化结果展示给 Labeler
  → Labeler 确认后预填到目标字段
```

| 角色 | 职责 |
|------|------|
| OWNER | 在模板 Designer 中配置 LlmTrigger 组件（选择 Provider、编写 Prompt、指定目标字段） |
| OWNER | 在 Designer 预览模式下测试 LlmTrigger 输出 |
| LABELER | 在标注工作台手动触发，查看结果，确认后预填 |

**关键约束**：LlmTrigger 输出只作为参考，不自动提交，必须经 Labeler 确认。

#### 场景 3：Pre-Annotation / 预标注（额外加分项）

```
LABELER 在标注工作台点击「AI 预填」按钮
  → 系统读取任务的 AI 审核配置（复用 Provider + Prompt）
  → 调用 LlmGateway
  → 返回整题建议答案（suggestedAnswerJson + fieldSuggestions）
  → Labeler 查看建议，选择性采纳
```

| 角色 | 职责 |
|------|------|
| OWNER | 无需额外配置，复用 AI 审核配置中的 Provider |
| LABELER | 手动触发，查看建议，选择性采纳到答案中 |

**与 LlmTrigger 的区别**：

| 维度 | LlmTrigger（课题要求） | Pre-Annotation（加分项） |
|------|------------------------|------------------------|
| 粒度 | 字段级，一个组件对应一个字段 | 题目级，一次生成所有字段建议 |
| 配置位置 | 模板 Designer 中拖入组件 | 复用任务的 AI 审核配置 |
| Provider 来源 | 组件内嵌 providerId | 任务 AI 审核配置中的 providerId |
| 触发方式 | 点击组件上的按钮 | 点击「AI 预填」按钮 |
| 输出 | 单字段值 | 整题 suggestedAnswerJson |

### 4.3 LLM Provider 管理与隔离

**归属**：OWNER 私有管理，每个 OWNER 只能看到和使用自己创建的 Provider。

**隔离规则**：
- `llm_providers` 表需增加 `owner_id` 字段。
- OWNER A 创建的 Provider，OWNER B 不可见、不可用。
- OWNER 配置 AI 审核或 LlmTrigger 组件时，只能选择自己的 Provider。
- SYSTEM_AGENT 执行 AI 预审时，使用任务 OWNER 配置的 Provider。

**Provider 生命周期**：

```
OWNER 新增 Provider（baseUrl + apiKey + modelName）
  → OWNER 测试连通性
  → OWNER 启用 Provider
  → OWNER 在 AI 审核配置 / LlmTrigger 组件中选择该 Provider
  → SYSTEM_AGENT / LABELER 运行时调用该 Provider
  → OWNER 可随时停用（停用后不可用于新配置，已配置的任务需更换）
```

### 4.4 LLM 调用的限流与安全

| 限流层级 | 说明 | 配置者 |
|----------|------|--------|
| Provider 级 | 平台全局 QPS 限制 | OWNER（Provider 配置中） |
| 任务级 | 单任务每分钟调用上限 | OWNER（AI 审核配置中） |
| 用户级 | 单用户每分钟调用上限 | OWNER（Provider 配置中） |

**安全约束**：
- API Key 加密存储，不明文返回前端，不写入日志。
- Prompt 和 rawResponse 必须保存，确保可追溯。
- 所有 LLM 调用产生 AgentRun 记录。

## 五、角色与业务流程的交互关系

### 5.1 核心业务链路中的角色参与

```
OWNER 创建任务 → 导入数据 → 搭建模板 → 配置AI审核 → 配置奖励 → 发布任务
                                                                    ↓
LABELER 浏览任务广场 → 领取题目 → 在线作答 → 保存草稿 → 提交答案
                                                              ↓
SYSTEM_AGENT 接收提交 → 构造Prompt → 调用LLM → 结构化输出 → 写入AI结果 → 推进状态
                                                                          ↓
REVIEWER 查看待审列表 → 参考AI结果 → 终审通过/打回 → 冲突仲裁 → 选择金标
         ↓(打回)                                        ↓(通过)
LABELER 查看打回理由 → 修改重新提交              OWNER 查看看板 → 导出金标数据
```

### 5.2 状态机中的角色触发权限

### 5.4 奖励机制中的角色分工

```
OWNER 配置奖励规则（unitReward + rewardCurrency）
  ↓ 任务发布时冻结规则快照
LABELER 提交答案 → 进入审核流程
  ↓
REVIEWER 终审通过 → 系统发布 SubmissionApproved 事件
REVIEWER 选择金标 → 系统发布 GoldenSelected 事件
  ↓
系统消费事件 → 生成正向 rewardLedger → LABELER 可查看奖励
```

| 环节 | 角色 | 动作 | 说明 |
|------|------|------|------|
| 配置规则 | OWNER | 创建任务时设置奖励规则 | 单条通过奖励金额、虚拟币种名、是否对 Labeler 可见 |
| 规则冻结 | 系统 | 任务发布时快照当前规则 | 后续规则变更不影响已发布任务的历史流水 |
| 触发奖励（通过） | REVIEWER | 终审通过 submission | 发布 `SubmissionApproved` 事件 |
| 触发奖励（金标） | REVIEWER | 冲突仲裁选择金标 | 发布 `GoldenSelected` 事件 |
| 结算奖励 | 系统 | 消费事件，生成 rewardLedger | 幂等检查，同一 submission 只计一次 |
| 查看奖励 | LABELER | 我的贡献页 | 累计奖励、奖励流水、各任务明细 |
| 查看统计 | OWNER | 任务看板 | 该任务的总奖励发放情况 |

#### 奖励规则

- 通过计奖，打回不计。
- 同一 submission 只能有一条正向奖励（先通过后又选为金标不重复计）。
- 冲突仲裁只奖励金标提交者，非金标提交者不计奖励。
- 支持冲正（负向流水），用于异常情况的奖励回收。
- ADMIN 和 REVIEWER 不参与奖励配置和查看。

### 5.5 多级审核流转

课题要求实现「多级审核（初审/复审/终审）」，系统通过 `reviewLevel` 和 `ReviewLevelEscalationService` 支持：

```
[Labeler 提交] → [AI 预审]
   ├─ AI PASS → [PENDING_FINAL]
   │              ├─ 初审通过（reviewLevel=1） → 升级到复审（reviewLevel=2）
   │              │     └─ 复审通过 → 升级到终审（reviewLevel=3）
   │              │           └─ 终审通过 → [APPROVED / 金标]
   │              └─ 任意级别打回 → [REJECTED → Labeler 修改]
   └─ AI FAIL / MANUAL_REQUIRED → [PENDING_FINAL]（Reviewer 可见 AI 建议）
```

#### 配置方式

- 通过 `labelhub.review.default-max-level` 配置审核级数（默认 1 = 单级终审）。
- 设为 2 = 初审 + 终审，设为 3 = 初审 + 复审 + 终审。
- 每级通过后自动升级到下一级，分配新的 Reviewer。
- 任意级别打回直接 REJECTED，Labeler 可见打回理由。
- 只有最高级别通过才触发 APPROVED 和奖励事件。

#### 各级审核员的职责

| 级别 | 定位 | 关注点 |
|------|------|--------|
| 初审（Level 1） | 基础质量筛查 | 格式合规、必填完整、明显错误 |
| 复审（Level 2） | 内容准确性 | 答案正确性、与题目的相关性 |
| 终审（Level 3） | 最终把关 | 综合判断、边界 case、金标选择 |

> 注：所有级别的审核员都是 REVIEWER 角色，区别在于被分配到的 reviewLevel 不同。系统不区分"初审员"和"终审员"的角色类型，而是通过 ReviewTask 的分配来控制。

## 六、接口权限控制规则

### 6.1 鉴权机制

- 所有业务接口通过统一 JWT Auth Filter 鉴权。
- Filter 从 token 中提取 userId、roles、tokenVersion。
- 角色变更后旧 token 失效（tokenVersion 校验）。
- 未登录访问业务接口返回 401。
- 无权限访问返回 403。

### 6.2 各角色可访问的 API 前缀

| 角色 | 允许的 API 路径前缀 |
|------|---------------------|
| ADMIN | 全部已认证业务 API；`/api/v1/admin/**` 为管理员专属管理 API |
| OWNER | `/api/v1/tasks/**`, `/api/v1/datasets/**`, `/api/v1/templates/**`, `/api/v1/ai-review-configs/**`, `/api/v1/rewards/**`, `/api/v1/exports/**`, `/api/v1/llm/triggers/**`, `/api/v1/llm-providers/**` |
| LABELER | `/api/v1/market/**`, `/api/v1/assignments/**`, `/api/v1/submissions/**`, `/api/v1/contributions/**`, `/api/v1/llm/triggers/**` |
| REVIEWER | `/api/v1/reviewer/submissions/**`, `/api/v1/reviewer/conflict-groups/**`, `/api/v1/agent-runs/**` |
| 公开 | `/api/v1/auth/login`, `/api/v1/auth/register`, `/api/v1/auth/refresh` |

### 6.3 资源级权限

- OWNER 只能操作自己创建的任务及其关联资源。
- LABELER 只能操作自己领取的 assignment。
- REVIEWER 全局可审核所有任务的待审提交。
- ADMIN 可跨角色访问和操作业务数据，但必须遵守各业务模块状态机、幂等和审计规则。

## 九、LLM Redis Stream 异步化补充

当前业务型 LLM 调用统一进入 Redis Stream 队列，覆盖 AI 自动预审、Pre-Annotation 预标注和 LlmTrigger 字段级辅助。Controller 和提交链路只创建业务记录、AgentRun 和队列消息，随后由 `LlmTaskWorker` 消费消息并调用 `LlmGateway`。

队列消息只保存 `taskType`、业务 ID、`agentRunId`、`traceId` 等调度字段，不保存完整 Prompt、答案内容或 API Key。MySQL 仍是状态和结果的唯一可信来源；Redis Stream 只承担异步调度、pending 恢复和消费确认职责。

Provider 连通性测试不进入 Redis Stream，仍保持同步调用，以便 OWNER 在配置页面即时判断 Provider、API Key 和模型是否可用。
