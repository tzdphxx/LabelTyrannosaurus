# AI Coding 工作流记录文档

## 概述

本文档记录本项目采用的系统化 AI Coding 工作流，旨在通过**事前调研 → 分层分析 → 架构先行 → 渐进开发 → 质量门禁 → 闭环反馈**，充分发挥不同模型的能力优势，实现高效、可控、可持续的代码生成。

工作流中大量使用 AI Agent Skill 来标准化和提效，每个环节按需通过 `find-skills` 发现并加载对应的 Skill。

---

## 0. 事前调研与可行性验证

在实际编码之前，对项目涉及的技术栈与业务领域进行系统性调研，降低技术选型风险。

### 0.1 技术栈调研

- 评估候选框架 / 库的社区活跃度、版本稳定性、生态成熟度
- 对比不同技术方案的优劣（如状态管理选型：Zustand vs. Redux vs. Jotai）
- 确认与现有系统的兼容性（Node 版本、浏览器支持范围等）
- 记录关键依赖的已知坑点与 Breaking Changes

### 0.2 业务领域调研

- 梳理同类产品的功能设计与交互模式（竞品分析）
- 确认涉及的专业术语与业务规则（如标注规范、审核流程等）
- 与相关方对齐对核心流程的理解

### 0.3 技术预研 / PoC

- 对不确定的技术点编写概念验证代码（如 Canvas 标注实现、WebSocket 通信方案）
- 验证关键依赖的 API 是否如预期工作（通过 `context7_query-docs` 查询官方文档）
- 产出调研结论文档或在 `agent.md` 中记录约束条件

**目的**：将不确定性消化在编码之前，规避后期因选型失误导致的返工。

## 1. 需求分析（双模型分层分析）

### 1.1 粗粒度分析（小模型）

使用轻量级模型对原始需求进行初步梳理，快速提取关键功能点、核心实体与大致流程。产出物为一组结构化的需求条目清单。

**目的**：快速收敛需求范围，过滤噪音信息，为大模型的深度分析提供结构化输入。

### 1.2 细粒度分析（大模型）

将小模型产出的需求条目输入至能力更强的大模型进行深度分析，包括但不限于：

- 边界条件与异常场景识别
- 隐式依赖与前置条件挖掘
- 技术可行性评估
- 模块划分建议
- 数据流与状态流转推导

**目的**：生成具备工程落地价值的详细需求规格。

---

## 2. 生成需求文档（PRD）

基于双模型分析结果，整理并撰写完整的需求文档，内容包含：

- 项目背景与目标
- 功能列表与优先级
- 用户角色与权限模型
- 核心业务流程
- 非功能性需求（性能、安全、兼容性等）

---

## 3. 技术设计文档

在进入前端专属需求之前，补充技术设计环节（这是流程的关键补全），内容包括：

- **组件树设计**：页面层级、容器组件与展示组件划分
- **数据流设计**：状态管理方案选型与 store 结构定义
- **状态模型**：核心实体（Entity）的状态机定义（如任务状态：待处理 → 进行中 → 已完成 → 已审核）
- **API 契约**：接口路径、请求/响应类型、错误码约定
- **路由设计**：页面路由结构、嵌套路由、守卫逻辑
- **共享层规划**：类型定义、工具函数、常量枚举的模块归属

**输出物**：`DESIGN.md` 或 `architecture.md`

**目的**：确保多 Agent 并行开发前，所有模块对共享协议达成一致，避免后期集成冲突。

---

## 4. 生成前端专属需求文档

将通用需求文档进一步精炼为前端专属需求文档，聚焦于：

- 页面结构与路由设计
- 组件拆分方案
- 状态管理设计
- API 接口契约
- UI / UX 交互细节
- 响应式与适配策略

此文档作为前端开发的唯一需求来源，确保团队对界面侧的理解一致。

---

## 5. 生成 `agent.md` 文档

基于前端需求文档，编写面向 AI Agent 的指令文档 `agent.md`，内容包括：

- 项目技术栈与目录结构约定
- 编码规范与命名约定
- 关键业务逻辑说明
- 常用命令与调试方式
- Agent 行为约束（如禁止删除未确认的文件、必须遵循的导入路径规则等）
- 调研阶段确认的技术约束与已知坑点
- **上下文索引**：列出关联的文档路径（DESIGN.md、需求文档等），Agent 启动时按需加载

**目的**：让 AI Agent 介入项目时能快速理解上下文，保持一致的行为范式。

---

## 6. 共享层先行

在启动并行开发前，先由单一 Agent 或人工产出**共享基础层**：

- 类型定义文件 (`types.ts`)
- 工具函数库 (`utils/`)
- API 客户端封装（使用 `axios-wrapper-pro` Skill 生成）
- 枚举与常量 (`constants/`)
- Store 基础结构

确保各模块 Agent 在并行开发时引用的是同一套类型与接口，不产生依赖冲突。

---

## 7. 模块拆分与多 Agent 并行开发

### 7.1 模块化拆分

将需求按照功能域或业务边界拆分为多个独立模块，例如：

- 认证模块
- 数据看板模块
- 标注引擎模块
- 项目管理模块
- 设置与配置模块

### 7.2 创建计划与工作树

为每个模块创建独立的开发计划，并构建对应的工作树（Work Tree），允许多个 Agent 并行开发而互不干扰。

### 7.3 分阶段细化（P0 / P1 / P2）

每个模块的计划进一步按阶段拆解：

| 级别 | 目标 | 交付物要求 | 质量门禁 |
|------|------|-----------|---------|
| **P0** | 核心链路打通，基础功能可用 | 主流程跑通，无阻塞 Bug | 编译通过 |
| **P1** | 功能完善，边界覆盖 | 所有用例覆盖，错误处理 | 编译通过 + Lint 通过 + 单元测试通过 |
| **P2** | 性能优化，体验打磨 | 性能达标，交互细节完善 | 编译通过 + Lint 通过 + 测试通过 + Code Review |

> **质量门禁**：每个阶段的 PR/Merge 必须通过当前阶段要求的全部检查，否则不允许进入下一阶段。

### 7.4 任务粒度与重试机制

- 每个 Task 细化到可在 1-2 次 Agent 调用内完成
- 每个 Task 设置 `max_retries`（建议 2-3 次），超限则标记为失败并回滚到上一个已验证版本

---

## 8. UI / UX 优化

在核心功能完成后，进入页面优化阶段：

1. 使用 `find-skills` 查找与 UI 优化相关的 Skill
2. 加载 `ui-ux-pro-max` Skill，基于其提供的模板与策略生成**页面优化计划**
3. 按计划对页面进行：布局调整、交互细节打磨、响应式适配、动效补充
4. 结合 Figma 设计稿（通过 `figma-dev_get_figma_data` / `figma-dev_download_figma_images`）还原 UI 细节

**目的**：借助已沉淀的设计模式，系统化提升页面质量，避免凭感觉修改。

---

## 9. 测试策略

| 阶段 | 测试要求 |
|------|---------|
| **P0** | 不强制要求编写测试，但需确保核心逻辑可手动验证 |
| **P1** | 单元测试与代码**同步产出**，覆盖核心业务逻辑与边界场景 |
| **P2** | 补充集成测试、E2E 测试关键路径，补全边缘 case |

---

## 10. 进度文档同步

开发过程中同步更新进度文档，记录：

- 各模块当前阶段（P0 / P1 / P2）
- 已完成与进行中的 Task
- 阻塞项与风险
- 变更记录与决策日志

进度文档作为项目健康度的仪表盘，便于随时掌握全局状态。

---

## 11. 经验沉淀（LESSONS.md）

在进度文档之外，维护一份 `LESSONS.md`，记录：

- Agent 在执行过程中遇到的典型错误与根因分析
- 被证实有效的 Prompt 模式或工作流优化
- 项目中特定的规则与约束（如某些文件不可修改、某些目录有特殊约定）

**用途**：后续 Agent 启动时注入此文档内容，避免重复踩坑，持续提升代码质量。

## 使用的 Skill 汇总

| Skill | 用途 | 调用时机 |
|-------|------|---------|
| `find-skills` | 发现和查找可用的 Skill | 每个关键环节开始时，检索是否有适用的 Skill 可以加载 |
| `context7_resolve-library-id` / `context7_query-docs` | 查询库/框架的官方文档 | 技术栈调研、API 使用疑问、版本迁移 |
| `axios-wrapper-pro` | 生成生产级 Axios 封装（TS + 双重错误处理 + 数据脱壳） | 共享层先行阶段，构建 API 客户端 |
| `ui-ux-pro-max` | 生成页面优化计划，提升 UI / 交互质量 | P2 阶段或独立 UI 优化轮次 |
| `writing-plans` | 将需求拆解为多步骤执行计划 | 模块拆分前，将整体需求转化为可执行的 Task 序列 |
| `architecture-blueprint-generator` | 生成项目架构蓝图文档 | 项目初始化或架构重构时，输出完整的架构视图 |
| `vercel-composition-patterns` | React 组合模式（Compound Components、Render Props 等） | 设计复杂组件时，避免 props 爆炸 |
| `figma-dev_get_figma_data` / `figma-dev_download_figma_images` | 拉取 Figma 设计稿数据 / 下载资源 | UI 还原与设计稿验证 |
| `customize-opencode` | 编辑 opencode 自身配置（opencode.json、AGENTS.md 等） | 调整 Agent 配置、权限规则、MCP 服务 |

## 工作流总览

```
原始需求
  ↓
[0. 事前调研] ←── 技术栈调研 / 业务调研 / 技术预研 PoC
                     │  └─ context7_query-docs 查官方文档
                     └─ find-skills 搜索可用的 Skill
  ↓
[小模型] 粗粒度分析
  ↓
[大模型] 细粒度分析
  ↓
需求文档 (PRD)
  ↓
技术设计文档  ←── architecture-blueprint-generator 生成架构蓝图
  ↓
前端专属需求文档
  ↓
agent.md
  ↓
共享层先行  ←── axios-wrapper-pro 生成 API 封装
  ↓
writing-plans 将需求拆解为可执行计划
  ↓
模块拆分 → 工作树 → Agent 并行开发
  │              │
  │  P0(编译通过) → P1(编译+Lint+UT) → P2(编译+Lint+UT+CR)
  │                                   │
  │                                   └── ui-ux-pro-max 优化页面
  │  find-skills / context7 按需调用
  │
  └──→ 进度文档 + LESSONS.md  ←── 实时同步
```

---

## 总结

这套 AI Coding 工作流通过**事前调研**将技术风险前置消化，通过**技术设计文档**填补架构空白，通过**共享层先行**解决并行依赖冲突，通过 **Skill 生态**（`find-skills` 发现 + 按需加载）将最佳实践注入每个环节，通过**质量门禁 + 重试机制**控制产出质量，通过 **LESSONS.md 经验沉淀**形成持续改进闭环。最终实现从调研到交付的全流程可管控、可追踪、可迭代。
