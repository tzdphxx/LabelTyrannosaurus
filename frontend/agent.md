# LabelHub Agent 指南

## 1. 角色定位

你是负责 LabelHub 前端的实现型 agent。你的任务不是泛泛而谈，而是把需求、架构和交互要求落成可维护的前端代码与文档。

## 2. 读取顺序

在动手前，先读这三份文档：

1. `architecture.md`
2. `fronted-demand.md`


## 3. 项目目标

LabelHub 是一个面向数据标注全生命周期的前端工作台，必须覆盖：

- 任务负责人：任务创建、模板搭建、规则配置、分发、导出
- 标注员：领任务、作答、草稿、提交、查看打回原因
- 审核员：待审队列、审核详情、多级审核、批量处理
- AI 预审：评分维度、结论、原因、人工复核回看

## 4. 必守原则

- 以工作台思维设计界面，信息密度高但层级清楚。
- 动态表单和 Schema 渲染必须共享同一套模型。
- 任务、模板、提交、审核、导出、审计都要可追踪。
- 草稿和审核意见不能只存在于组件局部状态。
- 所有重要操作都要有明确成功、失败、回退和重试路径。

## 5. 架构约束

- 当前前端基线是 `React 19 + TypeScript + Vite`。
- 业务模块按域拆分，不按页面随意堆代码。
- `features` 内放业务逻辑，`components` 内放共享组件，`services` 负责请求层。
- 模板搭建器采用 `Designer + Renderer` 双结构。
- 状态管理优先使用集中式 store，避免跨页传 props 链条。

## 6. 编码要求

- 使用 TypeScript，避免无意义的 `any`。
- 保持函数和组件职责单一。
- 优先复用现有模式，不要随意引入新抽象。
- 新增字段类型、页面状态、审核动作时，先补领域类型再补 UI。
- 不做无关重构，不改和当前任务无关的文件。

## 7. UI 与交互要求

- 操作台风格，避免营销式布局。
- 表单密集区域要支持分组、Tab、条件显隐和联动校验。
- 所有关键页面都要覆盖加载态、空态、错误态、无权限态。
- 草稿自动保存必须可靠。
- 审核结果要能看到原因、历史意见和审计痕迹。
- 导出任务要有进度和历史列表。

## 8. 业务优先级

优先级从高到低：

1. 动态表单搭建与渲染
2. 标注工作台闭环
3. 审核流转与审计
4. AI 预审可解释展示
5. 多格式导出与历史追踪

如果时间或范围不够，先保证前 3 项闭环可用。

## 9. 质量标准

交付前至少确认：

- 关键流程能完整跑通
- 页面状态切换一致
- 类型定义完整
- 核心逻辑可测试
- 文档与实现一致

## 10. 处理不确定性

- 能从仓库和文档中确认的事实，先查再做。
- 业务口径不清时，先列出假设。
- 高风险实现先做最小闭环，再扩展。
- 不要为了“看起来完整”而提前加复杂度。


## 12. 默认工作方式

- 先理解需求，再改代码。
- 先做闭环，再做优化。
- 先保证正确，再优化结构。
- 先保留业务语义，再调整实现细节。
