# AI Coding 方法论与协作模式

## 1. 协作定位

本项目把 AI 当作工程协作工具使用，而不是把它当成一次性代码生成器。AI 参与的主要工作包括需求拆解、方案草拟、接口和状态流梳理、测试用例规划、问题定位、实现口径校准和回归检查。

项目开发时始终保留一个原则：AI 可以提出方案，但方案结论必须回到项目本身。凡是涉及任务状态、提交状态、审核策略、数据表结构、权限边界和前后端契约的内容，都需要结合实现、迁移记录和测试反馈确认后再进入开发结论。

这种协作方式解决了两个问题：

- 项目范围较大，单靠人工记忆容易遗漏状态流和模块边界。
- AI 容易根据通用经验扩展功能，需要用项目事实约束它的输出。

因此，AI Coding 的过程不是“让 AI 直接写完”，而是“让 AI 先帮助整理问题，再用项目反馈逐步收敛”。

## 2. 过程分阶段

### 2.1 需求拆解阶段

最早的输入是数据标注平台课题要求。AI 先帮助把需求拆成角色和业务链路：

- Owner 负责创建任务、配置模板、导入数据、发布任务和导出结果。
- Labeler 负责领取题目、保存草稿、提交答案和根据打回原因修改。
- Reviewer 负责查看待审队列、参考 AI 预审结果、通过或打回提交。
- Admin 负责用户、Provider 和平台侧管理能力。

这个阶段的重点不是写代码，而是明确主链路。经过多轮梳理后，项目收敛为“任务创建 -> 动态模板 -> 标注提交 -> AI 预审 -> 人工终审 -> 导出”的单人标注闭环。讨论中出现过更复杂的协作设想，但没有进入可验证的业务主线。

### 2.2 方案草拟阶段

需求拆清楚后，AI 主要用于生成候选设计：表单模板如何版本化、提交如何保存历史、AI 审核如何异步执行、人工审核如何接管、导出如何读取通过数据。

这个阶段会先让 AI 给出多个方案，再做取舍。例如：

- 动态表单选择“模板版本 + 后端强校验”，而不是只靠前端渲染。
- AI 审核选择“AgentRun 记录 + 异步队列 + 人工兜底”，而不是提交接口同步等待模型。
- AI 结果选择“策略化流转”，而不是固定只能人工或固定自动通过。
- 审核选择“任务级领取 + 提交状态条件更新”，而不是 Reviewer 从全量提交里随意抢审。

这些方案的共同目标是降低返工：先把状态、边界和失败场景想清楚，再进入实现。

### 2.3 实现计划阶段

进入实现前，AI 会把功能拆成可验证的小步骤。每个步骤都尽量对应一个明确反馈：

- 先补测试或接口约束，观察当前系统缺口。
- 再补最小实现，避免一次改动覆盖太多模块。
- 最后跑定向测试，确认状态流、权限、幂等和异常场景没有被破坏。

这个过程在后端表现最明显。比如动态表单答案校验一开始只在模板服务里比较完整，但提交主链路没有真正使用字段级校验。AI 先帮助补出“缺少必填字段应被拒绝”的测试，再把校验入口接入提交服务，最后用提交服务测试确认 Labeler 不需要 Owner 权限也能按绑定模板版本完成校验。

### 2.4 实现反馈阶段

开发过程中并不是每个 AI 建议都会被接受。比较常见的反馈有三类：

- **代码不匹配**：AI 建议的类名、字段或状态与项目实现不一致，需要回到现有实现重新命名。
- **范围过大**：AI 容易把课题扩展成更完整的平台能力，需要压回当前 Demo 可验收主线。
- **安全边界不足**：AI 可能只考虑 happy path，需要补充权限、状态条件更新、重试和审计。

例如 AI 审核最初可以被描述成“模型判断后给结论”，但实际实现时必须处理 Provider 能力、调用失败、结果解析失败、低置信度、媒体降级和人工兜底。后续 review 也按这种工程链路判断，而不是把 AI 审核看成一次模型调用。

### 2.5 口径收敛阶段

随着主链路逐步稳定，AI 被用于复核早期判断，找出和已验证链路不一致的说法。

收敛时遵循两个规则：

- 主流程优先覆盖能演示、能解释、能验证的链路。
- 早期讨论过的扩展能力作为背景，不影响主链路表达。

因此，AI Coding 过程记录重点呈现开发思路、方向修正和工程取舍。

## 3. AI 在项目中的具体作用

### 3.1 帮助拆解复杂链路

LabelHub 涉及任务、模板、数据项、领取、草稿、提交、AI 审核、人工审核、导出、奖励和看板。AI 的第一个价值是把这些模块按业务顺序串起来，帮助识别哪些是主链路，哪些是扩展能力。

这一步避免了开发时平均用力。最终主线聚焦 Owner、Labeler、Reviewer 的端到端业务闭环，并由 Admin 提供平台管理、Reviewer 创建、Provider 配置和审核分配支撑，保证主流程演示时能讲清楚每一步的输入、处理和输出。

### 3.2 帮助生成候选方案

AI 在方案阶段会快速给出多种设计方式，例如同步调用模型还是异步队列、前端校验还是后端校验、审核结果是否允许自动流转。团队再根据项目复杂度、阶段目标和交付稳定性做取舍。

最终选择往往更保守：能配置但默认人工兜底，能异步但保留运行记录，能动态但后端强校验。这些取舍让系统既有亮点，又不牺牲可靠性。

### 3.3 帮助发现不一致

开发中经常出现“设想说一套，实现变成另一套”的情况。AI 被用来反向检查开发口径，例如：

- 是否让已经收敛掉的复杂标注协作影响主链路表达。
- 是否把 AI 审核写成固定只给建议，而忽略后端已有策略化流转。
- 是否只描述前端动态表单，而漏掉后端模板版本校验。
- 是否把导出描述成任意导出，而不是审核通过后导出。

这些检查让过程记录更贴近已验证链路，而不是停留在早期设想。

### 3.4 帮助补充验证思路

AI 还用于整理测试策略。比如提交链路重点验证模板版本、答案校验和重复提交；AI 审核重点验证策略、重试和人工兜底；审核链路重点验证领取归属、状态条件更新和打回重提。

这些验证不是单纯为了测试覆盖率，而是为了保证功能亮点都有行为支撑。

## 4. 协作中的约束

为了防止 AI 输出偏离项目，开发中给 AI 设置了几个约束：

- 先读现有文档和实现，再提出方案。
- 不凭空新增状态、角色、错误码或数据库字段。
- 不让早期方案影响正在实现的主链路。
- 不把模型输出直接当作最终业务结论。
- 不把敏感配置写入日志、快照或过程材料。
- 修改接口或状态流时同步考虑前端展示和后端校验。

这些约束让 AI Coding 保持在工程协作范围内，而不是变成自由发挥。

## 5. 形成的开发习惯

随着模块逐步收敛，团队形成了比较稳定的工作方式：

1. 先描述业务问题，而不是先写类名或接口名。
2. 再让 AI 给出方案和边界条件。
3. 用项目事实筛掉不适配方案。
4. 把保留下来的方案拆成小步实现。
5. 用测试、页面流程或接口反馈确认行为。
6. 回写过程记录，保留主链路中可解释、可验证的内容。

这种方式最适合本项目这类“功能多、状态多、AI 参与多”的工程。它既利用了 AI 快速整理和生成的能力，也通过项目事实和验证反馈控制了 AI 的发散。
