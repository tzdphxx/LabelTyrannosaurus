# 前端基础工程与 Owner 工作台 AI 使用过程

## 1. 初始计划

前端最早需要解决的不是某一个页面的样式，而是能否把 Admin、Owner、Labeler、Reviewer 稳定带入各自工作台。AI 参与的第一步是把需求拆成“身份入口、角色路由、公共布局、状态承载、业务页面”的顺序，避免一开始就把多角色页面、权限和业务状态混在一起。

初始方案采用先跑通基础工程，再逐步接入业务模块的节奏：

- 登录入口承载账号密码登录和身份注册，注册流程支持 Owner 与 Labeler 创建工作账号。
- 角色首页、顶部导航和侧边导航先统一，业务页面只关心自身职责。
- 业务状态进入集中 store，页面局部状态只保留弹窗、临时输入和短生命周期交互。
- 服务层以异步形态组织数据读取，并用 mock/real 模式隔离页面编排和接口来源。

这个阶段的取舍解决了两个问题：一是角色权限和导航不会散落在各个页面；二是 Admin、Owner、Labeler、Reviewer 的流程可以在同一套工作台框架里保持一致。

## 2. 执行记录

### 2.1 基础工作台

AI 先帮助梳理最小可运行闭环：访问应用后进入登录页，用户通过账号密码登录或注册进入对应工作台，未登录访问业务页面会回到登录入口，已登录用户不能直接进入其他角色页面。

执行中保留了几个边界：

- 登录态通过 token、角色和用户信息持久化，刷新后可恢复认证状态。
- 角色判断以当前登录角色为准，不在页面里重复写权限判断。
- 导航项从角色配置生成，页面不各自维护菜单。
- 无权限、空态、错误态使用统一状态组件承接。

认证层最终收敛为统一 HTTP Client、Bearer Token、401 refresh、角色首页跳转和登出清理，页面不直接处理 token 细节。

### 2.2 Owner 任务闭环

Owner 阶段的核心目标是让任务负责人能看到任务概览、维护任务草稿、关联模板、查看导入预览并完成发布前校验。AI 在这里主要承担流程拆解和状态边界设计：

- 任务列表、任务详情、进度和状态操作归入任务状态。
- 创建编辑中的基础信息、关联模板、导入预览和发布校验归入草稿状态。
- 仪表盘统计和重点任务归入看板状态。
- 页面只发起动作和展示反馈，不直接持有多份业务副本。

Owner 工作台的数据集导入按“文件上传 + 本地解析预览 + 发布校验”组织。前端支持 JSON、JSONL、XLSX 解析，生成字段映射、样例行和异常信息；real 模式下先上传数据集文件并记录文件 ID，再把解析预览用于任务配额、题目预览和发布前置判断。

## 3. Review 记录

开发过程中 AI 主要帮助识别三类风险。

第一类是角色边界风险。基础路由如果只靠页面入口隐藏，用户仍可能通过地址直接进入其他角色页面，因此需要统一守卫和角色重定向。

第二类是状态重复风险。Owner 创建任务时，基础信息、模板选择、导入预览和发布按钮都依赖同一份草稿。如果每个组件各自维护状态，会出现预览显示通过但发布校验失败的情况，因此统一放入草稿状态。

第三类是页面堆叠风险。Owner 页面容易变成表单、表格和卡片的简单堆放。AI 在 review 中推动页面按“概览、主操作区、状态反馈”组织，让任务负责人能快速判断当前任务是否可发布、哪里有异常。

## 4. 测试记录

基础工作台验证重点：

- 未登录访问业务入口时回到登录页。
- 已登录访问其他角色入口时回到自身首页。
- 四类角色看到不同侧边导航。
- 退出后清空登录状态。

Owner 工作台验证重点：

- 仪表盘统计、最近任务和重点任务能正常展示。
- 任务列表可按关键词和状态筛选。
- 状态操作有确认和反馈。
- 任务创建流程中缺少模板、缺少数据或导入存在阻断问题时不能发布。
- 草稿、导入预览和发布校验在页面切换中保持一致。

构建和静态检查在部分阶段受本地 Node 环境影响，过程记录按当时环境记录执行状态，没有把环境受限的检查写成已通过。

## 5. 收敛结果

该阶段形成的是前端工作台骨架和 Owner 主流程。AI 的作用不是一次性生成页面，而是把“角色入口、导航复用、状态边界、服务边界、发布校验”拆成可逐步验证的闭环。

Owner 相关能力收敛为：看板了解进度，任务管理处理状态，任务编辑维护草稿，导入预览提供发布依据，发布校验阻止不完整任务进入发布流程。
