# 动态表单与 Labeler 标注闭环 AI 使用过程

## 1. 初始计划

动态表单是前端最容易失控的部分。AI 在方案阶段先把问题拆成两层：一层是模板设计器如何搭建 schema，另一层是运行态表单如何消费同一份 schema。最终选择“Designer + Renderer + 可序列化 schema”的结构，而不是让设计态和作答态各自维护字段模型。

这个选择的原因很直接：

- Owner 设计模板后，Labeler 必须能直接用同一份结构作答。
- Reviewer 回看提交时，也需要基于提交快照只读展示答案。
- 表单显隐、校验、联动等规则如果写成函数，保存、传输和回放都会困难。
- 拖拽状态、选中状态、画布滚动等运行时信息不能混入业务 schema。

因此动态表单先限制能力边界：优先完成基础输入、选择、展示、分组和 Tab，再纳入富文本、文件选择、JSON 编辑和 LLM 辅助展示等物料表达。

## 2. 执行记录

### 2.1 schema 与物料边界

AI 先帮助定义字段类型、字段 key、标题、默认值、属性、校验规则、显隐条件、联动规则和 children 结构。开发过程中反复校验的原则是：schema 能保存、能回填、能被 Renderer 消费，不能包含组件实例、函数或拖拽临时对象。

物料中心承担三件事：

- 生成默认字段节点。
- 判断字段能否放入某类容器。
- 为 Renderer 提供组件映射和基础配置。

这样做解决了物料扩展问题。新增物料时不需要在设计器、渲染器和工作台里分别写一套判断，只要让物料定义进入统一注册机制。

### 2.2 模板设计器

设计器阶段的 AI 使用集中在拖拽规则和状态拆分上。拖拽添加、画布排序、容器承载和属性编辑都通过 schema tree 操作完成，不直接操作页面结构。

执行中修正过一个明显问题：模板设计页一度变得过大，页面同时承担路由、store 编排、拖拽解析、画布节点、属性面板、预览和工具函数。AI review 后将低层 UI、拖拽工具、schema 工具和属性编辑拆开，页面只保留编排职责。

拆分后的收益是：

- 设计器页面更容易理解。
- 画布、属性面板、schema 管理面板可以独立调整。
- 增加条件显隐、联动规则和 schema 导入时，不需要继续堆叠页面文件。

### 2.3 Labeler 标注工作台

Labeler 阶段的主线是“领取任务、进入工作台、作答、保存草稿、提交、查看结果、打回后修改”。AI 先把这个流程拆成任务广场、工作台、我的提交三块，并要求它们共享同一套任务、题目、草稿和提交状态。

工作台采用三栏结构：

- 左侧题目导航展示进度和当前题。
- 中间区域使用动态表单 Renderer 作答。
- 右侧展示任务信息、保存状态、提交动作和打回意见。

草稿保存没有放在组件局部状态里，而是通过服务边界写入浏览器本地持久化。这样刷新页面后仍能恢复草稿，同时保持与真实接口服务一致的调用形态。

提交前校验重点放在用户可感知的问题上：缺失必填字段、存在未完成题目、表单校验失败时能跳到第一道错误题。这样 Labeler 不需要猜测为什么不能提交。

## 3. Review 记录

动态表单 review 关注四个风险。

第一，Designer 和 Renderer 分裂。如果设计器内部结构和运行态结构不同，每增加一个物料都要维护两套逻辑，因此必须以业务 schema 作为唯一输入。

第二，规则不可序列化。任意函数校验和脚本表达式虽然灵活，但会破坏保存、回放和跨端消费，因此只保留可配置的显隐、必填、枚举和基础联动。

第三，草稿丢失。标注员作答链路长，刷新、切题和提交失败都不能清空输入，因此保存失败只提示问题，不覆盖当前编辑值。

第四，打回重提覆盖旧记录。打回后的修改要生成新的提交记录，旧答案和旧意见保留为历史快照，避免审核原因和提交版本无法追溯。

## 4. 测试记录

动态表单验证重点：

- Owner 可以添加、排序、编辑和删除字段。
- 分组和 Tab 能承载子字段。
- 必填、显隐和基础联动规则能在预览态生效。
- schema 保存后能重新读取并回填设计器。
- Renderer 使用同一份 schema 输出结构化答案。
- 只读模式能用于审核详情回看。

Labeler 验证重点：

- 任务广场可搜索、筛选和领取任务。
- 已领取任务能进入工作台。
- 作答内容能手动保存和自动保存。
- 刷新后能恢复草稿。
- 提交失败不丢失当前答案。
- 打回任务能看到来源、原因和上一轮意见。
- 重新提交不覆盖旧提交记录。

## 5. 收敛结果

这一阶段让前端从“页面表单”收敛为“schema 驱动的数据生产工具”。AI 的主要价值体现在边界控制：设计态、作答态、预览态和审核只读态都围绕同一份 schema 工作，草稿和提交状态通过统一链路流转。

这一阶段形成的前端能力是：Owner 搭模板，Labeler 用模板作答，提交时产出结构化结果，审核可以基于提交快照回看，不依赖模板版本变化。
