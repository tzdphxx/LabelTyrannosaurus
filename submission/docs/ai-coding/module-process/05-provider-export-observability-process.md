# Provider、导出与可观测 AI 使用过程

## 1. 初始计划

这个模块覆盖三类平台支撑能力：

- LLM Provider 管理：模型接入、安全配置和能力声明。
- 导出：将审核通过的数据生成可下载文件。
- 可观测：记录 AI 运行、审计日志、trace 和导出文件。

AI 在计划阶段先把三者联系起来：Provider 决定 AI 能力边界，AI 运行结果进入审核链路，审核通过后的数据进入导出，所有关键动作需要可追溯。

## 2. 执行记录

### 2.1 Provider

执行时首先确定 Provider 由管理员维护。原因是 Provider 包含密钥、模型地址、请求头和限流配置，不应由普通任务页面直接暴露。

Owner 只读取已启用 Provider，用于任务 AI 配置。这样既保留任务侧灵活性，又集中控制密钥和能力声明。

Provider 相关执行重点：

- 密钥只在创建、更新和测试时提交。
- 保存时加密。
- 响应时只展示是否已配置。
- 敏感请求头统一脱敏。
- Provider 能力用于决定是否启用多模态输入。

### 2.2 导出

导出最初容易被设计成“导出任务下所有提交”，但 review 后收敛为只导出审核通过数据。这样能保证导出文件代表已完成审核的结果。

导出过程按两条链路组织：一条是任务级直接导出，同步生成文件并返回短期下载链接；另一条是异步导出任务，记录导出状态、文件引用和历史结果。两条链路都围绕任务维度和审核通过提交组织。

导出格式按 JSON、JSONL、CSV、XLSX 拆分。空结果也生成合法文件，方便调用方统一处理。

导出摘要中可以包含 AI 审核和人工审核信息，但这些信息不决定是否可导出。导出范围只由审核状态决定。

文件生成后写入对象存储并返回下载地址，导出任务自身只记录配置、状态、结果文件和错误摘要，不反向推动提交或审核状态。

### 2.3 可观测

AI 执行、审核动作、导出文件都需要有记录。可观测设计重点不是简单打日志，而是把业务事件和运行记录串起来：

- AI 执行有运行记录。
- 审核结果有关联提交。
- 导出文件有任务和提交范围。
- trace 能连接请求、异步任务和审计记录。

## 3. Review 记录

Review 阶段发现的重点问题包括：

- Provider 响应不能暴露密钥或敏感 Header。
- AI 失败时要保留脱敏后的错误摘要。
- 导出创建失败不能留下不一致状态。
- 直接导出和异步导出都必须遵守同一套审核通过数据范围。
- 下载链接由文件存储层签发，导出服务不把文件流和审核状态耦合在一起。
- Labeler 和 Reviewer 不应调用 Owner/Admin 导出能力。
- 审计参数不合法会阻断导出，需要保证关键字段完整。

这些问题让平台支撑模块从“功能能用”进一步转向“安全、可追溯、可恢复”。

## 4. 测试记录

测试规划分为三组：

### 4.1 Provider

- 管理员能创建和测试 Provider。
- 管理员能启用和停用 Provider。
- Owner 只能看到启用项。
- 响应不包含密钥明文。
- 敏感 Header 被脱敏。

### 4.2 导出

- Owner 能导出自己任务下审核通过的数据。
- Admin 能导出任意任务数据。
- Labeler 和 Reviewer 不能导出。
- 空结果生成合法文件。
- 多种格式都能生成并返回文件记录。
- 直接导出能返回文件 ID、文件名、校验信息、下载链接和导出数量。
- 异步导出能查询任务历史、执行状态和结果文件。

### 4.3 可观测

- AI 任务带有运行记录。
- 异步任务携带 trace。
- 审核动作写入审计记录。
- 导出文件与任务关联。
- 失败场景保留可诊断错误，不暴露密钥。

## 5. 收敛结果

Provider、导出和可观测模块共同形成平台支撑层：Provider 让 AI 能力可控，导出让审核结果可输出，可观测让过程可解释。

AI 在这个模块中的价值主要体现在安全边界和异常场景枚举。它帮助把“能调用模型、能生成文件”扩展为“密钥不泄露、结果有范围、失败可诊断”。
