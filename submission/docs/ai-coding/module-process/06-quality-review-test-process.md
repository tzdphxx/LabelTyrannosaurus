# 质量审查、优化与测试 AI 使用过程

## 1. 初始计划

主链路逐步稳定后，AI 的主要作用从功能生成转向质量检查。检查目标包括：

- 权限是否过宽。
- 状态流是否可能并发覆盖。
- 列表和统计是否存在重复查询。
- 异步任务是否能安全重放。
- 过程记录是否与已验证链路一致。
- 测试是否覆盖主业务闭环。

这一阶段不再追求新增功能，而是让主链路更稳定、更清晰。

## 2. 执行记录

### 2.1 安全审查

AI 辅助梳理了端到端接口流程，按 Owner、Labeler、Reviewer、Admin 角色分别检查访问边界。检查发现需要重点关注 Reviewer 读权限、Owner 自注册、导出权限、Provider 错误信息和 Prompt Injection。

执行后的收敛原则是：

- 写权限和读权限都要校验归属。
- AI 直通策略必须受风险和置信度约束。
- Provider 错误信息要脱敏。
- 用户输入进入 Prompt 时要被视为不可信内容。

### 2.2 性能与 SQL 审查

AI 参与了 SQL 和服务访问模式审查，重点发现列表和统计类接口中的 N+1 查询、重复 count、日期函数影响索引、审核打回路径并发保护不足等问题。

方案选择上，优先使用批量查询、条件更新和范围谓词，而不是引入大范围缓存或额外分布式锁。

这类取舍的原则是：先消除确定的数据库往返和状态覆盖问题，再考虑缓存。缓存不能替代正确的查询和状态机。

### 2.3 异步任务可靠性

LLM 队列审查时，AI 帮助把“消息是否可重复消费”拆成几个判断：

- 消息里的运行记录是否仍存在。
- 运行记录是否已经终态。
- 业务结果是否已经完成。
- 是否需要新建运行记录继续执行。
- 失败后是否保留 pending，等待人工认领或重试。

这一阶段形成“数据库是事实源，队列是信封”的原则。

### 2.4 过程口径同步

AI 还用于同步开发过程中的口径变化，例如复杂协作能力收敛为单题单活跃标注员链路、AI 审核从固定建议调整为策略流转、导出范围收敛为审核通过数据。

这些变化会回写到对应模块过程记录中，保证计划、执行、review 和测试材料讲的是同一条业务链路。

## 3. Review 记录

质量 review 的核心结论：

- 审核打回和通过都应使用当前状态条件更新，避免覆盖终态。
- 不可变模板版本适合缓存，但领取资格和审核队列不能缓存。
- 列表接口应批量加载关联数据，避免分页越大越慢。
- 统计查询应使用索引友好的时间范围。
- 集成测试应覆盖真实安全过滤器、数据库迁移、Redis 和 HTTP 路由。
- 过程记录应只围绕能闭环的能力展开。

这些 review 结论不是单纯代码风格建议，而是围绕可靠性、性能、安全和链路一致性。

## 4. 测试记录

测试规划按层次拆分：

### 4.1 单元测试

- 模板 schema 校验。
- 提交答案校验。
- AI 流转策略。
- AgentRun 状态守卫。
- Provider 加密和脱敏。
- 导出格式生成。

### 4.2 服务测试

- 任务创建和发布前置条件。
- Labeler 领取、草稿、提交。
- Reviewer 通过、打回、修订。
- AI 审核失败转人工。
- 导出只读取审核通过数据。

### 4.3 集成测试

集成测试规划覆盖真实 Spring Boot 环境下的关键链路：

- 认证和角色权限。
- Owner 任务配置。
- Labeler 主链路。
- Reviewer 主链路。
- AI 配置和异步状态。
- 导出、审计和通知 smoke check。
- MySQL 迁移和 Redis 队列基础能力。

集成测试不调用真实外部 LLM 和对象存储，而是保留真实应用装配和数据库状态。

## 5. 收敛结果

质量审查阶段让项目从“功能完成”进一步收敛到“流程稳定”。AI 的价值主要体现在系统性检查：它能快速列出权限、并发、性能、缓存、异步和链路一致性的风险，再由项目事实决定修复顺序和验证重点。

质量收敛后形成的共识是：主链路必须稳定，AI 能力必须可控，过程记录必须贴合现有实现。
