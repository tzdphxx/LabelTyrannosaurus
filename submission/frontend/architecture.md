# LabelHub 前端架构文档

## 1. 文档目的

本文档定义 LabelHub 前端的目标架构，用于把 `fronted-demand.md` 中的需求落到可实现、可维护、可扩展的前端工程结构中。它回答四件事：

- 前端系统由哪些层和模块组成
- 核心业务流如何在前端流转
- 动态表单、审核流、导出、AI 预审如何拆分
- 代码组织、状态管理、接口契约和错误处理如何统一

本文档面向前端实现，不讨论后端数据库设计和服务内部实现。

## 2. 架构目标

- 支持任务负责人、标注员、审核员三类角色的独立工作台
- 支持 schema 驱动的动态表单搭建与渲染
- 支持任务分发、标注、审核、AI 预审、导出全链路闭环
- 支持草稿、回退、审计、历史记录等可追溯能力
- 支持后续扩展新的标注类型、审核维度和导出格式

## 3. 技术选型

前端实现基线沿用当前仓库的 `React 19 + TypeScript + Vite`。

推荐的业务组件和能力分工如下：

- UI 组件库：Ant Design
- 状态管理：Zustand
- 路由：React Router
- 拖拽编排：@dnd-kit/core
- Schema 渲染：Formily 或等价 schema 驱动方案
- 请求层：统一封装的 API Client
- 表单校验：schema 校验 + 运行时校验双层保障

如果后续需要接入 AI 预审结果，前端只消费结构化返回，不直接承载 Prompt 生成逻辑。

## 4. 系统边界

### 4.1 前端负责

- 登录后角色识别与导航切换
- 任务列表、详情、编辑、提交、审核、导出等交互
- 动态模板搭建器
- Schema 渲染器
- 草稿缓存与回填
- AI 预审结果展示
- 审计日志和历史记录展示
- 错误态、空态、加载态、无权限态

### 4.2 前端不负责

- 任务调度策略的服务端执行
- AI 模型推理与评分计算
- 数据持久化与版本存储
- 导出文件生成的后端计算过程

## 5. 总体分层

前端采用“应用层 - 业务层 - 能力层 - 基础设施层”的分层方式。

```text
src/
  app/            # 应用入口、路由、全局布局、权限守卫
  pages/          # 页面级组件
  features/       # 业务域模块
  components/     # 共享组件
  schemas/        # 表单 schema 和渲染配置
  services/       # API 封装和数据访问
  stores/         # 全局状态
  hooks/          # 通用 hooks
  utils/          # 工具函数
  types/          # 领域类型
```

### 5.1 应用层

负责：

- 路由初始化
- 布局装配
- 角色路由守卫
- 全局消息、主题和权限上下文

### 5.2 业务层

按域拆分：

- `task`：任务创建、发布、分发、状态追踪
- `template`：模板搭建、schema 编辑、预览
- `labeling`：标注工作台、草稿、提交
- `review`：审核队列、审核详情、批量处理
- `export`：导出任务、历史、下载
- `audit`：审计日志、操作轨迹
- `ai-review`：AI 预审结果、评分维度、结论展示

### 5.3 能力层

沉淀可复用能力：

- 表单渲染引擎
- 拖拽编排引擎
- 校验引擎
- 权限判断
- 进度与草稿管理
- 文件上传与预览
- 导出任务轮询

## 6. 领域模型

前端统一使用以下核心领域类型，作为页面、接口和状态的共同语言。

```ts
type Role = 'owner' | 'labeler' | 'reviewer' | 'system';

type TaskStatus =
  | 'draft'
  | 'publishing'
  | 'published'
  | 'paused'
  | 'ended'
  | 'claimed'
  | 'in_progress'
  | 'submitted'
  | 'pending_review'
  | 'approved'
  | 'rejected';

type ReviewDecision = 'pass' | 'reject' | 'revise' | 'manual_review';

interface Task {
  id: string;
  title: string;
  description: string;
  status: TaskStatus;
  ownerId: string;
  templateVersion: string;
  deadline?: string;
}

interface SchemaNode {
  id: string;
  type: string;
  label: string;
  props: Record<string, unknown>;
  rules?: ValidationRule[];
  children?: SchemaNode[];
}
```

### 6.1 关键对象

- `Task`：任务元信息和状态
- `Template`：模板定义、版本、预览配置
- `SchemaNode`：动态表单节点
- `Submission`：标注提交结果
- `ReviewRecord`：审核结果和审核意见
- `ExportJob`：导出任务及其进度
- `AuditEvent`：审计轨迹

## 7. 路由架构

路由按“角色入口 + 业务页 + 详情页 + 编辑页”组织。

### 7.1 基本结构

```text
/login
/app
  /owner
  /labeler
  /reviewer
```

### 7.2 典型路由

- `/app/owner/dashboard`
- `/app/owner/tasks`
- `/app/owner/templates`
- `/app/owner/tasks/:id/edit`
- `/app/owner/tasks/:id/review`
- `/app/labeler/market`
- `/app/labeler/workbench/:taskId`
- `/app/labeler/submissions`
- `/app/reviewer/queue`
- `/app/reviewer/tasks/:id`
- `/app/export/jobs`
- `/app/audit/logs`

### 7.3 路由原则

- 列表页负责筛选、搜索、批量操作
- 详情页负责只读信息与历史
- 编辑页负责 schema、规则、发布配置
- 工作台页负责高频操作和草稿恢复

## 8. 状态管理架构

### 8.1 状态分层

- 服务端状态：任务、模板、审核结果、导出任务、审计记录
- 客户端状态：当前角色、导航折叠、筛选条件、局部编辑状态
- 持久化状态：草稿、最近访问、用户偏好

### 8.2 Zustand Store 划分

建议拆成以下 store：

- `authStore`：登录态、角色、权限
- `taskStore`：任务列表、详情、状态切换
- `templateStore`：模板草案、schema 节点、预览状态
- `labelingStore`：工作台题目、草稿、提交状态
- `reviewStore`：审核队列、审核动作、意见
- `exportStore`：导出任务、进度、历史

### 8.3 状态原则

- 服务端数据与本地编辑状态分离
- 草稿状态必须可恢复
- 审核动作必须有明确结果和原因
- 高并发操作要有幂等提示和按钮防抖

## 9. 动态表单架构

这是整个平台的核心。

### 9.1 设计器和渲染器分离

- `Designer`：负责拖拽、编排、属性编辑、结构调整
- `Renderer`：负责按照 schema 运行时渲染表单
- `Schema Registry`：负责把节点类型映射到具体控件

### 9.2 物料模型

物料按能力分组：

- 文本类：单行、多行、富文本
- 选择类：单选、多选、标签
- 媒体类：图片、文件、附件
- 结构类：分组、Tab、容器、ShowItem
- 智能类：LLM 交互组件、引用建议组件

### 9.3 渲染流程

1. 读取模板 schema
2. 解析节点树
3. 应用字段联动与条件显隐
4. 生成运行态表单
5. 执行运行时校验
6. 输出结构化提交结果

### 9.4 校验策略

- 静态规则：必填、长度、正则、枚举
- 动态规则：依赖字段、条件联动、组合约束
- 自定义规则：业务函数校验
- 提交校验：整单校验 + 局部定位

## 10. 工作流架构

### 10.1 任务负责人流

```text
创建任务 -> 搭建模板 -> 配置规则 -> 预览 -> 发布 -> 分发 -> 追踪 -> 导出
```

### 10.2 标注员流

```text
领取任务 -> 打开工作台 -> 自动保存草稿 -> 校验 -> 提交 -> 查看打回原因 -> 修改再提
```

### 10.3 审核员流

```text
进入审核队列 -> 查看详情 -> AI 预审参考 -> 审核决策 -> 批量处理 -> 留痕
```

### 10.4 流程要求

- 所有状态变更都要保留时间线
- 打回必须展示上游理由
- 多级审核需要展示当前层级和历史动作
- 任务状态切换要保持前后一致

## 11. AI 预审架构

前端把 AI 预审当作“可解释结果面板”，不是黑盒结果标签。

### 11.1 展示内容

- 总体结论
- 评分维度
- 每个维度的分值
- 命中原因
- 风险提示
- 推荐动作
- 原始返回内容

### 11.2 前端职责

- 展示 AI 预审结果
- 标注 AI 与人工结论差异
- 允许在审核页对照原数据和 AI 建议
- 保留审计记录入口

### 11.3 失败兜底

- AI 未返回结果时展示人工审核入口
- AI 评分缺失时降级为普通审核视图
- 超时或异常时提示“结果暂不可用”

## 12. 导出架构

### 12.1 导出类型

- JSON
- JSONL
- CSV
- Excel

### 12.2 导出模式

- 异步任务提交
- 轮询任务状态
- 历史列表查询
- 结果下载

### 12.3 字段映射

前端提供字段映射配置界面，允许：

- 选择导出字段
- 重命名字段
- 控制是否包含审核记录
- 控制是否导出原始数据

## 13. 权限架构

### 13.1 权限粒度

- 页面级：角色是否可进入
- 操作级：按钮是否可见
- 字段级：敏感字段是否显示
- 数据级：任务是否可访问

### 13.2 权限处理原则

- 前端只做显示控制，不做安全可信判定
- 所有关键操作仍需后端校验
- 无权限场景必须统一提示

## 14. 交互与体验标准

- 核心流程必须可撤销或可回退
- 重要动作必须有二次确认
- 草稿必须自动保存
- 页面切换不能丢失正在编辑内容
- 长列表必须支持筛选和分页
- 表单宽字段必须支持分组和多 Tab

## 15. 错误处理

### 15.1 错误类型

- 网络错误
- 权限错误
- 业务校验错误
- 运行时异常
- 导出任务失败
- AI 预审失败

### 15.2 处理原则

- 错误信息贴近用户操作
- 表单错误定位到字段
- 页面级错误提供重试入口
- 异步任务错误保留上下文

## 16. 性能架构

### 16.1 优化目标

- 列表页可稳定承载高频查询
- 动态表单在中大型 schema 下保持可用
- 拖拽编辑器在复杂模板下不卡顿
- 审核详情和预审结果加载可分段展示

### 16.2 优化手段

- 路由级拆分和懒加载
- 大表单分区渲染
- 结构化缓存与草稿复用
- 列表虚拟化或分批渲染
- 重计算字段缓存

## 19. 验收标准

前端架构是否成立，至少看这几条：

- 三类角色都能完成自己的主流程
- schema 设计器和渲染器共享同一份模型
- 草稿、审核、导出、审计都可追踪
- AI 预审结果能被清晰解释
- 目录结构、状态层和业务层边界清楚
- 新增一种字段类型时不需要改大量页面代码

## 20. 风险与约束

- 动态表单复杂度高，必须控制 schema 设计的自由度
- 草稿、提交、审核状态不能在前端重复造多个来源
- 导出和 AI 预审都是异步链路，前端必须处理长任务状态
- 版本兼容要靠 schema 版本和模板版本控制

## 21. 结论

LabelHub 的前端架构核心不是“页面堆叠”，而是“schema 驱动 + 工作流状态 + 多角色权限 + 可解释 AI 结果 + 可追溯导出”。只要把这五件事统一在同一套模型和模块边界里，后续扩展新标注类型、新审核规则和新导出格式都会比较平稳。
